# F002: Persistence Contracts

Status: technical specification revision 1 — approved 2026-09-26; not implemented
Last updated: 2026-09-26

Part of the [technical plan](technical-plan.md), explicitly approved as technical specification revision 1 on 2026-09-26. These contracts specify the approved behavior; no runtime code or schema is created by this document.

## Data boundaries

Use lowercase text UUIDv4 identities independent of labels and Git hashes. Revision identity is a distinct UUIDv4 with predecessor revision and SHA-256 content digest; do not use branch-local integer equality as proof of identical revisions. Deterministic tests inject IDs and timestamps. Canonical JSON hashing recursively sorts keys by UTF-16 code units, preserves array order, serializes finite JSON numbers with JavaScript JSON semantics, rejects undefined/unsupported values, and uses UTF-8 without whitespace. Strings are not Unicode-normalized. Hash the complete typed revision envelope, including identity, predecessor, authorship, owner/scope, relationships and deletion flag, excluding its digest field. Binary snapshot digests hash exact bytes; logical equality compares typed records rather than SQLite file bytes. Hashes detect integrity differences, not approval or authorship by themselves.

Approved table groups and minimum contracts:

| Tables | Required data and invariants |
| --- | --- |
| `project_meta` | Project/repository identity, schema/format versions, accepted reconciliation generation; installation details excluded. |
| `records`, `record_revisions` | Stable ID, kind, head revision; revision predecessor, author, owner/scope, deleted flag, content digest and bounded payload. Retain revisions only for active reconciliation, required history/evidence, or immutable Reports. |
| `relationships` | Stable edge ID, source/target IDs, relationship type and revision; real foreign keys to record identities. Validate allowed types, cardinality, scope and cycles in controlled operations. |
| `workers`, `grants`, `approvals` | Stable worker identity separate from activations; issuer, grantee, operation/scope, grant lineage and revocation; approval subject ID plus exact approved revision. Historical imported grants do not activate local authority. |
| `mutations` | Operation ID, actor, grant references, base/result revisions and content digests. Runtime-owned provenance, never proof of authority solely because a child submitted it. |
| `branches`, `baselines`, `imports`, `import_items` | Direct parent, repository, baseline/checkpoint digest, generation, immutable submitted-state digest, parent expectation, review dispositions, authorization and atomic import receipt. |
| `replica_revisions`, `outbox`, `receipts`, `evaluations` | Origin/author, record ID/revision/digest, destination and generation; exact durable receipt; separate parent-authored evaluation. Replicated definitions are excluded. |
| `attachments`, `evidence_refs` | SHA-256, size, repository-relative immutable path, required record/revision references and media type. |
| `checkpoints`, `integration_facts` | Independent checkpoint/operation IDs, repository and code references; actual merge result and frozen Report completion facts. No self-hash field. |
| `deletions`, `reconciliation_decisions` | Deleted identity/revision, generation and dependencies; explicit retirement decision and authority. |

Portable tables are the groups above. Keep attempts, next-retry timers, installed trust activation, resume authorization, open connection/process identity, filesystem paths, and operation-journal details in explicitly local tables (`local_attempts`, `local_trust`, `local_execution`, `local_operations`). Empty those four tables in the staged snapshot; never clear them in the live source. Portable outboxes retain destination identity, ID/revision/digest and pending obligation; receipts and historical grants remain evidence, not locally active permissions. Raw conversations/logs and secrets are never stored in this project schema.

Representative record kinds: Project, Delivery, Feature, Task, Report, Progress, Alert, Escalation. Do not add production scheduling states. Allow Feature-to-Project, Delivery-to-Project, Task-to-Feature/Task, and Report-to-Feature/Project relationships for fixtures. Task-to-Delivery is unsupported pending R-06; do not encode a permanent Feature-only SQL column. An unsupported relationship must fail explicitly, not fall back to an invented Feature.

Labels are display metadata, never foreign keys. The spike permits duplicate labels but disambiguates review output by kind and full stable ID; no branch-local renumbering of identities.

Use explicit NOT NULL, boolean CHECKs, kind/type allowlists, unique IDs, and composite uniqueness for record/revision and delivery receipts. Historical ID/digest references may outlive current records and are explicitly historical, not broken foreign keys to current rows. Live relationships and current-head references require referential integrity. `record_revisions` owns versioned outgoing relationship content; `relationships` is its transactionally maintained current index, not an independently editable second source.

Bounded payload validators: Project/Delivery/Feature carry title and summary; Task adds assigned worker and representative Active/Paused status; Report carries Draft/Submitted/Completed, summary, outcome and evidence references; Progress carries completed/current/next text and blockers; Alert/Escalation carry message, severity and references. Approvals bind the exact subject revision. Definition draft edits never replace an approved revision pointer. Only the coordinator's successful integration finalizer may move Submitted to Completed and freeze the Report. This models persistence guards, not the full production transition graph.

## Controlled operations

Every operation receives a runtime-established actor context, project/repository/worktree scope, operation ID, and expected revision where applicable. A worker cannot grant itself authority by supplying an actor ID, editing a grant row, or presenting imported history. Scripted actors use these same service boundaries; privileged test setup may inject corruption to verify detection.

Core interfaces: `readRecord`, `mutateRecord`, `softDelete`, `createBranchBaseline`, `proposeImport`, `reviewImportItems`, `applyImport`, `publishReplica`, `receiveReplica`, `acknowledgeReplica`, `prepareCheckpoint`, `publishCheckpoint`, `restoreCheckpoint`, `recoverOperation`, `reconcileDeletedRecords`, and `migrateFixture`. Each returns a typed success or a boundary-specific failure with permitted diagnostics, and durable operation identity for mutating retries.

Authorize reads as well as writes. Recheck grant lineage/revocation on each use. Prevent owner/author/approved-revision changes through ordinary payload updates. Use prepared parameters, foreign keys, STRICT tables, WAL and synchronous FULL for live databases; confirm settings by reading them back. Disable dynamic extension loading. Short writes use `BEGIN IMMEDIATE`, explicit rollback on failure, and bounded busy handling. SQLite provides one writer at a time, not application authority: see [transaction semantics](https://sqlite.org/lang_transaction.html).

Use a 1,000 ms SQLite busy timeout and return a typed Busy result without an unbounded retry loop. Application retries preserve operation IDs and recheck actual state and authority. The harness injects a zero timeout for deterministic lock tests. Coordinator grants permit only enumerated operations and resources: actors cannot edit grants, branch registries, baseline metadata, import receipts or closure facts as ordinary records. Grant revocation and final application share the authority lock so revocation cannot race between validation and commit. Hostile shell/file access enforcement remains R-05; service tests do not prove OS isolation.

Interfaces share `ActorContext`, `OperationId`, `ExpectedRevision`, and typed record/envelope inputs. Reads return the authorized record/revision; mutations return the new revision and operation receipt; proposals return a digest-bound item list/dispositions; application returns one durable import receipt; replication returns an exact storage receipt; checkpoint/restore/recovery return checkpoint identity plus operation phase and required reconciliation. Error codes: Denied, StaleRevision, Conflict, InvalidRelationship, InvalidFormat, IntegrityFailure, MissingEvidence, ExpiredBaseline, ProposalChanged, OperationIdReused, Busy, and UncertainOutcome. Rejected mutations leave domain state unchanged; permitted audit records may be appended separately.

## Baselines and imports

Capture the complete portable parent snapshot and logical digest at branch creation under the parent's operation boundary, before adding the new branch's baseline reference. Parent-owned registry fixes lineage, authority and baseline identity. Retain immutable baseline bytes at `.lazycode/baselines/sha256/<digest>.sqlite`, Git-tracked while any branch or descendant requires them, and list their transitive evidence/baseline dependencies in the checkpoint inventory. Child initialization copies that baseline and installs new local worktree identity; it does not inherit local execution/trust. Branch names and Git merge-base alone are insufficient after amendments. Missing baseline bytes block import instead of guessing. Removal requires the same reference/recovery checks as other reconciliation cleanup.

Compare trusted baseline B, frozen child submission C, and current parent P by identity, revision lineage and canonical content. Examine actual persisted records and relationships, not just reported mutations. Reject unknown schema objects, project mismatch, forged metadata and malformed provenance before interpreting an import.

The user confirmed whole-record conflict granularity on 2026-09-26 ("yes it fits"): a logical record is the update unit, including its owned relationships. If child and parent both changed it from B to distinct revisions, return the entire proposed import for reconciliation, even if different fields changed. Exact same revision and digest already received is idempotent; equal payload with distinct provenance is not automatically identical. Parent-only changes remain unchanged. Inserts require new identity and valid authority; edit/delete conflicts block. Relationship validation covers the combined result. No field-level auto-merge is included.

Unauthorized items require explicit receiving-parent dispositions and reasons. Determine dependence through persisted relationships, declared operation dependencies, approved contract references, and parent review. Structural validity alone cannot prove narrative independence; uncertain dependence returns for correction. Omissions do not import unauthorized payloads or any dependent valid-looking changes. Retain scoped evidence and digests for the disposition without leaking unauthorized content to actors who lack read access.

Bind the proposal to baseline, frozen submission, parent canonical-state digest, authority revision, and decisions. At application, lock and recheck these inputs. Any canonical parent drift invalidates the proposal, even if independent, and requires reproposal preserving the newer state; replica-only receipt updates do not invalidate canonical state. Apply the validated change set and receipt in one transaction. A lost response followed by the same operation ID/digest returns the stored result; reusing an ID for different content fails. Frozen local ledgers are coordinator-owned evidence. A submitted ledger/hash is cross-checked against the parent's issued grants and trusted branch session; hashes do not authenticate a malicious copied ledger. Untrusted/new-installation branch provenance requires reconciliation/confirmation before import.

## Replication

Authoritative mutation and its outbox entry commit together. Replicas retain the same author, ID and revision; receiving-parent evaluation is a separate record. Deliver through an in-process/scripted transport with injected failures; production network transport is deferred.

Store each delivered authorized revision and receipt atomically before acknowledging. Duplicate ID/revision/digest returns the same receipt; same revision with a different digest fails. Out-of-order revisions may be stored, but must not regress the displayed current head. Unknown or divergent ancestry stays visibly pending reconciliation. No acknowledgment claims storage of an unstored revision. Sender removes pending delivery only after checking a matching destination/project/generation/ID/revision/digest receipt.

Keep replica storage separate from canonical record heads. Eligible kinds are Progress, Alert, Escalation and Submitted Report; receiver cannot mutate the author's payload. Parent-issued author/origin grants and branch generation must match. A received revision may be durably stored and acknowledged with status `stored_pending_ancestry` if its predecessor is unavailable; do not display it as the current complete state yet. Advance the replica head only through a verified predecessor chain from the known head. A fork in that chain is a reconciliation conflict. Retain earlier revisions when required by active delivery or evidence. Each outbox carries an immutable revision, so acknowledgment of r1 cannot clear pending r2. Deletion is itself a versioned envelope subject to the same checks.

Canonical imports recognize already stored replica revisions without duplication and do not overwrite a newer replica head with an older imported revision. Canonical acceptance and latest live reporting remain distinguishable. Outbox retries use the exact origin/destination/project/generation/ID/revision/digest tuple. Restored pending obligations remain visible but cannot transmit until local trust/reconciliation permits it. Cleanup cannot remove state needed by an unresolved receipt or pending revision.

## Snapshots and attachments

For every evidence write, stage bytes inside the worktree, hash and size-check them, fsync, then rename into the content-addressed attachment directory before committing its database reference. Existing digest paths are immutable and verified before reuse. Reject absolute/traversal paths, symlinks at any component, nonregular files, and references outside the allowed evidence/baseline roots. Required evidence is not acknowledged or published until bytes are present and validated. Orphan files after a crash are harmless until reviewed cleanup; no automatic deletion of unknown files.

Snapshot preparation uses a dedicated connection and Node's backup API into a unique local staging directory. Writers on other connections may continue; the result is a committed consistent cut, not necessarily the instant backup started. Capture the code/index candidate and pause changes to its evidence/approval scope while preparing its checkpoint; unrelated progress may continue. Derive the attachment inventory from the completed snapshot, never a second live query. Hold an attachment-retention lease until staging/publication settles.

In the staged copy only, empty local tables and compact with VACUUM so excluded local rows are not left in free pages; set a standalone journal mode, close all connections, and require no WAL/SHM dependency. Run both `integrity_check` and `foreign_key_check` plus schema, record, grant-history, and evidence validation. Compute snapshot digest after all changes and close. [SQLite's PRAGMA reference](https://sqlite.org/pragma.html) distinguishes database integrity from foreign-key checking; [VACUUM](https://sqlite.org/lang_vacuum.html) rebuilds the file. This sanitization is not a mechanism for storing secrets and later trying to scrub them: secrets are never admitted to the project database.

Manifest v1 fields: format/schema version, project/repository ID, independent checkpoint UUID, snapshot SHA-256 and size, logical state digest, branch/baseline/generation IDs, code reference, and sorted required-file inventory (path, kind, SHA-256, size). It contains no own-manifest digest and no enclosing commit hash. The snapshot's `checkpoints` table records prior checkpoint facts, not its own final file digest or commit hash; current-checkpoint identity belongs in the manifest and is recorded in the live database after publication. Inventory includes required attachments, retained baselines and commit-preservation bundles, excluding the manifest itself. All fields derive from the frozen state and verified files. File timestamps do not establish integrity or authority.

The code reference is `containing-commit` with a digest of sorted tracked path/mode/blob-ID entries excluding only `.lazycode/checkpoint/`, `.lazycode/attachments/`, and `.lazycode/baselines/`. Include ordinary project documentation, configuration, source and tests; reject tracked local-state files. Explicit historical code references use repository ID and exact Git object ID. Resolve `containing-commit` from the checkpoint's source commit, never from a branch name. Dirty unrelated changes are not swept into a checkpoint; unexpected edits stop the affected operation for the user. Required uncommitted code is not described as recoverable committed work.

Install prepared files under the fixed tracked paths only from validated staging. A filesystem journal identifies old/new digests so interruption between replacements is detectable. Restores read one Git tree, where the files form a committed set, not an unchecked working-directory mix. Failed publication leaves the preceding committed checkpoint usable; local recovery does not overwrite newer live data with it.

## Git/database coordination and amended commits

Serialize canonical parent imports and Git publication through a durable per-worktree coordinator gate. Maintain `.lazycode/local/operations/<operation-id>/journal.json` with input digests, expected old ref, candidate tree/commit IDs, phase, and staged-file checksums; use write/fsync/rename and directory sync where supported. Validate rather than blindly replay this journal after restart. Reads requiring code/database agreement and affected new mutations remain stopped while publication is incomplete; unrelated worktrees continue.

| Phase | Durable action and recovery rule |
| --- | --- |
| G0 Prepared | Record authority, expected parent Git ref and canonical DB digest, frozen child submission and accepted import proposal. Stage the candidate DB by applying the exact proposal to a consistent parent copy. No live parent domain changes yet. |
| G1 Candidate | Use `git merge-tree --write-tree` and a temporary index to form the explicit two-parent merge tree for clean code merges; replace generated database/manifest paths with the validated parent result even if Git sees no binary conflict. Generated-path conflicts may be resolved only with that prepared result; any other conflict blocks. Check the code-path delta against the child contract and reviewed dependency/exclusion decisions. Build candidate commit with `git commit-tree`; persist its object ID before publication. Ordinary commits/amendments use the same staged-tree discipline with appropriate parent list. Unresolved code/document conflicts return to their authorized owners; no automatic conflict resolution. |
| G2 Ref published | Revalidate authority, parent DB and expected old ref under the gate; use compare-and-swap `git update-ref` to publish the known candidate. If interrupted, actual ref equal to candidate proves publication; equal to old ref permits the same prepared attempt after revalidation. An unexpected ref stops for reconciliation. Never create another merge merely because the response was lost. |
| G3 DB applied | With the gate still held, apply accepted DB changes and import receipt once in a live SQLite transaction against the recorded parent digest. Preserve unrelated local/replica tables. If Git was published but this transaction was not, replay only the proven accepted operation. Unexpected domain drift or manual edits block recovery instead of replacing the live DB. |
| G4 Finalized | Record actual merge ID, parent acceptance and one Completed Report revision in a transaction. The child's submitted account stays unchanged; the runtime attaches mechanical completion facts. Refresh only expected checkout paths after verifying no unexpected user edits. Queue the following closure checkpoint; release the gate after code/live-state consistency is restored. |
| G5 Closure saved | Publish the next checkpoint carrying G4 facts, using the ordinary checkpoint publication protocol. Report finalization is idempotent by integration operation ID. If the checkpoint is interrupted, G4 remains recoverable locally and finalization is visibly not yet portable. |

Git does not transact with SQLite. These phases prove detectable, resumable completion, not simultaneous atomicity across systems. A portable snapshot inside the merge may still show Submitted; its pending integration descriptor plus the enclosing commit's actual parents lets restoration identify the completed Git action and reconstruct the mechanical finalization after reconciliation. The portable descriptor retains operation ID, accepted proposal digest, expected parent/child commit IDs, affected Report IDs, and historical approval reference, without local paths or the eventual enclosing hash. An incomplete ordinary snapshot does not pretend a pending merge succeeded. No execution automatically resumes during recovery.

[`git merge-tree`](https://git-scm.com/docs/git-merge-tree) provides merge-tree computation, [`git commit-tree`](https://git-scm.com/docs/git-commit-tree) constructs commits from trees and explicit parents, and [`git update-ref`](https://git-scm.com/docs/git-update-ref) checks the previous ref value before replacement. Git mechanics must be tested in temporary repositories; they are not changes to this planning checkout.

After a merge, the closure checkpoint uses the next editable implementation-commit slot. Ordinary progress checkpoints amend the eligible slot with a new checkpoint ID. Never amend a published or parent-integrated commit; preserve explicit merge parents and avoid squash. Reject an attempted amendment when the boundary registry disallows it. Do not auto-push.

Before replacing a commit still referenced by evidence, preserve its reachable objects in a self-contained Git bundle, referenced as a content-addressed attachment in the replacement checkpoint. Verify the bundle in a fresh repository and confirm the required exact commit/tree can be recovered. This also preserves the old checkpoint content. [Git bundles](https://git-scm.com/docs/git-bundle) carry objects for offline recovery. Bundles may duplicate historical snapshot/attachment bytes and grow substantially; measure consecutive amendments explicitly. Optimizing bundle packing is later work; failure to preserve required code blocks publication.

Verification results bind to exact already-created commits and live outside the tested commit until a later checkpoint/parent captures them. They never claim to validate the new commit that stores them. Rerun required suites after changes, including an amended candidate; keep results in the runtime evidence store/replica rather than repeatedly amending the same candidate to insert its own test result. Closure-checkpoint creation does not imply fresh suite success; its deterministic integrity checks and any subsequent full-suite run are separately recorded.

## Reconciliation cleanup

The receiving parent's authorized reconciliation operation evaluates a fixed deletion set under the canonical-state gate. Preserve anything referenced by current records, approved definitions, immutable Reports/evidence, unresolved Findings/decisions, active baselines, outboxes/receipts, or recoverable operations. If usefulness is uncertain, retain it with the blocking reason for parent review. No wall-clock TTL alone proves uselessness.

Delete eligible payload/revision/index rows transactionally while retaining a compact deletion marker `(record_id, deletion_revision, branch_scope, generation)`. Historical audit ID/digest references do not by themselves require the entire payload; retained evidence does. A marker blocks update/insert resurrection in a still-supported generation. Remove orphan revision/mutation payloads only under the same usefulness test; retain required decision summaries.

Generations are per receiving-parent branch scope. To retire generation g, every registered source using it must have zero unsettled imports/outboxes/uncertain operations and have reconciled, or have a separately authorized retirement decision preserving any required unfinished work. The receiving parent cannot retire work it lacks authority over; escalate through parents to the user as necessary. Store the decision, advance the generation floor, and remove eligible markers in one transaction. Coordinate generation changes down direct-parent edges; no root-wide silent retirement. A lost response is handled through the reconciliation operation receipt.

An expired source is rejected before any of its rows are considered, including apparently new IDs. Fresh reconciliation preserves its old database, computes its changes against the retained old baseline if available, and reviews them against the current parent. Missing old baseline requires supervised reconstruction; never treat all old records as fresh inserts. Accepted remaining work starts with a new registered baseline/generation. Merely rewriting the source's generation number cannot authorize it.

Physical row removal is mandatory for eligible records/markers. SQLite may retain allocated free pages until compaction; do not promise immediate file-size shrinkage. Snapshot compaction reclaims that space. Git history is not rewritten. Automated evidence-file garbage collection remains outside scope; file inventory/retention correctness is still tested.

## Restore, compatibility and migration

Portable restore validates manifest/file digests, expected schema objects, both SQLite checks, required code and baseline dependencies in an isolated staging directory before creating a live database. Never import arbitrary SQL dumps or enable extensions. Restore active Task fixtures as Paused through recorded restoration revisions; retain previous history, deliberate pauses and unresolved blocks. Clear local trust/execution tables; flag raw history unavailable. Imported grants require explicit local activation, and activation never resumes work by itself.

Current-installation crash recovery first inspects the live WAL/database and G0–G5 journals; it does not roll back to Git simply because a newer live state is uncheckpointed. Notify the user of interrupted work and require the established restart authorization before execution. Routine deterministic state reconciliation does not grant restart permission. Tests exercise the guard/state only, not a production scheduler or UI.

Use `application_id` fixed to ASCII LZCD (0x4c5a4344), `user_version` as schema version, and manifest portable format version 1. All three must agree with the allowlisted supported layout. Unknown/newer versions are inspected read-only for identification only, then rejected for write/import. Cross-version branch comparison requires explicit migration of all relevant copies to the same supported schema; do not mix layouts.

Exercise synthetic schema v1 to v2 by adding `project_meta.migration_label` as non-null text with validated default `fixture-v2`. This metadata field is outside record revision envelopes, so immutable IDs/revisions/digests must remain identical. No real project migration occurs. Make a backup, migrate a separate copy in one transaction, validate row identities/revisions/relationships, and activate by a journaled file swap with all live connections closed. Crash before activation retains original; after swap inspect old/new file hashes and version, never rerun a half-inferred migration. Keep the original until activation is validated and explicitly settled. Unsupported migration paths and failed checks leave the source untouched. Production rollback across new writes and an indefinite migration matrix are deferred.
